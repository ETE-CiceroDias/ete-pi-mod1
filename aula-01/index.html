01 · Fundamentos

Arquitetura de Software

Antes de escrever uma linha de código, existe uma etapa que muitos iniciantes pulam — e que faz toda a diferença no resultado final: a arquitetura de software. Assim como um arquiteto projeta uma construção inteira antes de qualquer tijolo ser colocado, a arquitetura de software é o conjunto de decisões estruturais que define como um sistema vai ser organizado.

Ela determina quais são os componentes do sistema, como eles se comunicam entre si, quais são as responsabilidades de cada parte e como o sistema vai se comportar. A arquitetura não é o código — é o raciocínio que vem antes dele.

Um sistema sem arquitetura definida vira rapidamente aquilo que os desenvolvedores chamam de código espaguete — tudo misturado, ninguém sabe onde mexer, qualquer mudança quebra outra coisa.

02 · Organização

Modelo de Software

Quando um grupo de pessoas vai construir algo juntas, a primeira pergunta que surge é: por onde a gente começa? Quem faz o quê? No desenvolvimento de software, essa pergunta não é diferente.

Antes de escrever qualquer código, o time precisa decidir como vai trabalhar. Os modelos existem porque, sem um acordo sobre como o trabalho vai fluir, cada pessoa puxa para um lado, os prazos estouram e o produto final não corresponde ao que o cliente esperava.

Não existe um modelo perfeito para todos os casos — o que existe é o modelo certo para o contexto certo.

02b · Contexto

Metodologia Ágil

Um conjunto de valores e princípios — não uma ferramenta, não um processo. Uma forma diferente de pensar o desenvolvimento de software.

No final dos anos 90, o desenvolvimento de software vivia uma crise. Projetos grandes, planejados anos antes, chegavam ao final completamente fora do prazo, do orçamento e — pior — sem atender às necessidades reais dos usuários.

Em fevereiro de 2001, dezessete desenvolvedores se reuniram numa estação de esqui em Utah, EUA, e escreveram o Manifesto Ágil — um documento curto que mudou a indústria de software para sempre.

A ideia central é simples: entregar valor cedo e com frequência, colaborar com o cliente, responder a mudanças em vez de seguir um plano rígido.

03 · Ciclo

Ciclo de Desenvolvimento
de Software

Todo software tem uma história — nasce de uma necessidade, é planejado, construído, testado, entregue e um dia deixa de ser usado. Esse caminho completo é o ciclo SDLC.

01 Planejamento

Tudo começa aqui. O time levanta a viabilidade do projeto, define objetivos, estima custos, prazos e recursos. É a fase das grandes perguntas: vale fazer isso? Como vai funcionar? Quem vai fazer?

02 Requisitos

Levantamento detalhado de tudo que o sistema precisa fazer. Inclui reuniões com o cliente, análise de necessidades e documentação funcional. A pergunta central: o que o software precisa fazer?

03 Design

Com os requisitos em mãos, o time projeta a arquitetura do sistema: banco de dados, interfaces, fluxos, componentes. É o momento de criar o blueprint antes de construir qualquer coisa.

04 Desenvolvimento

O código é escrito. Programadores implementam tudo o que foi planejado nas fases anteriores. É a fase mais longa e visível do ciclo — mas sem as anteriores, ela vira caos.

05 Testes

O sistema é verificado contra os requisitos originais. Bugs são encontrados e corrigidos. Testes funcionais, de performance, de segurança. Quanto mais tarde um bug é descoberto, mais caro fica corrigi-lo.

06 Implantação

O produto vai para produção — disponível para os usuários reais. Pode envolver migração de dados, treinamentos, configurações de servidor. É o momento de colocar no ar.

07 Manutenção

O software vivo precisa de cuidado constante: correção de bugs que só aparecem em produção, atualizações de segurança, melhorias de performance, novas funcionalidades. O ciclo nunca acaba — ele se reinicia.

04 · Modelo

Modelo em Cascata

O Modelo Cascata surgiu na década de 1970. Nele, o desenvolvimento acontece de forma linear e sequencial: primeiro levantam-se todos os requisitos, depois faz-se o design, em seguida o desenvolvimento, depois os testes, e por fim a entrega.

Cada fase só começa quando a anterior está concluída — como uma cascata que só corre para baixo, sem voltar. O problema é que o modelo assume que tudo pode ser previsto no início, o que raramente acontece na prática.

Se o cliente mudar de ideia ou um erro for descoberto tarde, o custo é alto. Foi exatamente por isso que o mercado foi buscando alternativas mais flexíveis — e nasceu o pensamento ágil.

04b · Modelo

Modelo Incremental

No modelo incremental, o sistema é desenvolvido e entregue em partes — cada parte é um incremento funcional do produto final. O cliente usa versões parciais do sistema desde cedo e fornece feedback real.

Diferente da cascata, o incremental admite que nem tudo pode ser previsto no início. Cada ciclo refina o entendimento do problema e ajusta o que vem a seguir. É a transição natural entre a cascata e o pensamento ágil.

Cada incremento passa por todas as fases do SDLC — planejamento, design, desenvolvimento, testes e entrega — mas aplicado a uma fatia menor e gerenciável do produto.

04c · Metodologia

Metodologia Ágil

Em 2001, 17 desenvolvedores insatisfeitos com os modelos rígidos se reuniram e escreveram o Manifesto Ágil — um conjunto de valores que mudou a forma como o mundo desenvolve software.

A metodologia ágil não é um método único — é uma filosofia de trabalho que valoriza entregas rápidas, colaboração com o cliente e adaptação constante à mudança. Em vez de planejar tudo antes de começar, o time aprende enquanto constrói.

O Manifesto Ágil estabelece 4 valores fundamentais: indivíduos e interações acima de processos e ferramentas; software funcionando acima de documentação extensa; colaboração com o cliente acima de negociação de contratos; responder a mudanças acima de seguir um plano.

Scrum e Kanban são as principais implementações práticas dessa filosofia — frameworks que traduzem esses valores em cerimônias, papéis e fluxos de trabalho concretos.

05 · Framework

O que é Scrum?

A ideia central do Scrum é simples: em vez de planejar tudo de uma vez e entregar no final, o time trabalha em ciclos curtos entregando partes funcionais com frequência. Isso permite identificar erros cedo, o cliente acompanha o progresso e o time melhora a cada ciclo.

O Scrum não é uma metodologia rígida — é um framework, uma estrutura flexível que o time adapta à sua realidade.

06 · Método

O que é Kanban?

Método ágil visual e de fluxo contínuo — surgiu nas fábricas da Toyota e foi adaptado para o desenvolvimento de software. Sem ciclos fixos, sem papéis obrigatórios.

kan
kanban · fluxo contínuo
Trabalho visual e contínuo. Novas tarefas entram à medida que outras são concluídas. Princípio fundamental: limitar o que está em andamento.
Kanban...

O Kanban não trabalha com ciclos fixos nem exige papéis definidos — o trabalho flui de forma contínua. Um princípio fundamental é limitar tarefas em andamento ao mesmo tempo, evitando sobrecarga e perda de foco.

Para projetos como o de vocês, o Kanban é o ponto de entrada mais natural pela sua simplicidade visual — é o que vocês vão montar no Trello hoje.

07 · Organização

Product Backlog

A espinha dorsal do desenvolvimento ágil. Lista viva e priorizada de tudo que o produto precisa ter.

Quem mantém o backlog é o Product Owner, mas o time inteiro contribui para refiná-lo. Diferente de uma lista de tarefas comum, o backlog é priorizado — o item com mais valor para o usuário ou negócio fica sempre no topo.

O backlog nunca está "pronto" — ele evolui com o produto. Novos itens entram, outros saem, prioridades mudam conforme o time aprende mais sobre o problema que está resolvendo.

Ordem de Prioridade

O backlog não é uma lista aleatória — cada item tem um lugar. O Product Owner ordena tudo de acordo com o valor que entrega ao usuário. No topo ficam as coisas mais importantes e urgentes. Lá embaixo, o que pode esperar.

Durante a Sprint Planning, o time pega os itens do topo do backlog — os mais prioritários — para trabalhar na Sprint. Por isso manter a ordem certa é fundamental.

Hierarquia do Backlog
01
Nível 1
Épico
Grandes funcionalidades ainda pouco detalhadas. Representam partes significativas do produto, amplos demais para caber em uma Sprint.
Ex: "Sistema de Cadastro" · "Módulo de Relatórios"
02
Nível 2
História de Usuário
Descreve uma funcionalidade do ponto de vista de quem vai usar o sistema. Formato: "Como [usuário], eu quero [ação] para [benefício]".
Ex: "Como visitante, eu quero me cadastrar com e-mail para acessar o sistema"
03
Nível 3
Tarefa
Ações concretas e técnicas para implementar cada história. Específicas, atribuídas a pessoas e estimadas em horas ou pontos.
Ex: "Criar formulário HTML" · "Configurar rota" · "Escrever teste"
